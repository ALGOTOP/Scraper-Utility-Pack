In the business-level dedupe logic (dedupe=business on GET /leads/export), I found two problems from testing against real data:

1. When multiple ads for the same business have identical scores, the tie-break isn't actually using anything deterministic. It's supposed to fall back to "most recent," but in a real batch where all ads were scraped in the same job, they share the same created_at timestamp down to the millisecond — so "most recent" can't break the tie, and whatever it's currently falling back to (insertion order? row id?) isn't documented or guaranteed stable. Two identical runs against the same DB state should always pick the same row. Please find out what it's actually keying on right now, make it explicit and deterministic (e.g. fall back to lowest id, or highest id — pick one and document it), and add a code comment stating the full tie-break order: score desc -> created_at desc -> id asc (or whatever we land on).

2. More importantly: when ties get collapsed, distinct final_urls are being silently thrown away. I had a real case where one business had 4 ads — 3 pointing to an iTunes link and 1 pointing to a Play Store link, all scored identically — and the dedupe kept one iTunes row and the Play Store URL just vanished from the export with no trace it ever existed.

Fix: the deduped row should still be one row per business (we only want to contact each business once), but add a new column, other_urls, that lists any other distinct final_url values from the collapsed ads for that business, semicolon-separated, excluding the URL that's already in final_url. If all collapsed ads share the same URL, other_urls should be empty/null. Update openapi.yaml, the generated zod schema, and leads.ts accordingly.
